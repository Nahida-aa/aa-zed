## 模块组织

### 目标

让**一次修改**（约等于一次 commit / 一次 review）所涉及的文件，在文件树上的跳转距离加权最小。

- 权重 = 修改频率。高频修改对优先压低距离，低频的可以牺牲。
- 推论：**一次提交应尽量落在少数相邻文件里**，review 时不必来回翻目录。

### 成本度量

把文件树里每一项（文件或文件夹）都视作占一格。跳转成本定义为：

| 情形 | 成本 |
|---|---|
| 同一文件 | `0` |
| 同一目录 | `n`（`n` = 该目录条目数） |
| 相邻目录 | `\|src\| + \|dst\| + 1` |
| 不相邻目录 | `\|src\| + \|dst\| + gap`（`gap` 为父层中两目录之间的条目数 + 1，通常 4～8） |

优化目标：

```math
min Σ 修改频率 × 跳转成本
```

### 目录大小约束

- **5 项**：友好
- **7 项**：常规上限
- **9 项**：应急极限

文件夹和文件**同权**——它们占同样的视觉高度。嵌套文件夹在父层只算 1 项。

超限时：优先把**低频访问**的条目下沉到子目录，而不是硬挤。

### 拆分原则

**1. 数据和逻辑同文件**

```rust
// 正确：Content 的定义、构造、同步在同一文件
pub struct Content { ... }
impl Default for Content { ... }
pub fn make_content(...) -> Content { ... }
```

```text
// 反例：把同一概念劈成两半
model/content.rs   // 只有 struct
service/content.rs // 只有操作
```

**2. 按编辑频率聚类，不按类型/操作分层**

先找“哪些文件会频繁一起改”，把它们放进同一文件或同目录。
不要按 `model/` + `service/` 这种抽象分层切——它把高频共改对推远。

**3. 高频对优先合并到同一文件**

成本从 `|src| + |dst| + gap` 压到 `0`，是收益最大的一类操作。

**4. 排序也是变量**

相邻目录成本为 `|src| + |dst| + 1`，不相邻要多付 4～8。高频互引的目录应在父层相邻。
若无法控制 IDE 排序，优先用“合并到同一目录”代替“调顺序”。

**5. 子目录只为低频项服务**

子目录降低父层 `|dir|`，从而压低所有经过父层的跳转成本。
但访问子目录内文件要多付一层，所以**只把内部高频互引、对外低频的簇下沉**。

### 反例

- **按语言机制拆**：`types/` + `ops/`、`model/` + `service/`。同一概念被劈开，改一次要跳两次。
- **顶层平铺 20+ 文件**：扫描成本过高，且无领域边界。
- **深层嵌套每层只有 1～2 文件**：跳转次数换来的只是文件数减少，不值。
- **按字母序排列高频互引的目录**：白白多付 4～8 个中间条目。

### 一句话

每个目录 5～7 项，类型与操作同文件，高频共改对同目录，低频项下沉到子目录。
用“一次提交需要审核的文件是否聚集”作为检验标准。
